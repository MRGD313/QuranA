# معماری QuranA

این سند تصمیم‌های اصلی و جریان داده را توضیح می‌دهد.

## جریان یک درخواست

```
کاربر (بله)
   │  یک واژه
   ▼
bale_api.getUpdates + iter_text_messages
   ▼
bot_handler.handle_update
   ├─ اعتبارسنجی ورودی و تشخیص خط فارسی/عربی
   ├─ normalize_word  (حذف اعراب، یکسان‌سازی الف/همزه/ة/ى)
   ├─ morphology.resolve_roots
   │     ├─ واژه‌های قرآنی با همان فرم نرمال
   │     └─ تطبیق مستقیم با ریشه‌های ثبت‌شده
   │           ├─ یک ریشه  → ادامه
   │           └─ چند ریشه → نمایش گزینه‌ها و انتظار انتخاب عددی
   ├─ search_service.search_root
   │     ├─ رخدادهای segments با root انتخاب‌شده
   │     ├─ بازیابی متن هر آیه از جدول ayat
   │     ├─ گروه‌بندی بر اساس (سوره، آیه) و حذف تکرار
   │     └─ مرتب‌سازی و محاسبه آمار
   ├─ report_generator.generate_report → فایل UTF-8
   └─ bale_api.sendDocument + sendMessage
```

## چرا دو منبع داده؟

- **متن قرآن** باید عیناً از منبع مرجع خوانده شود تا خروجی قابل استناد باشد.
- **تحلیل صرفی** باید از یک منبع زبانی مستقل باشد تا ریشه با حدس یا شباهت
  رشته‌ای تعیین نشود.
- ادغام این دو با شناسهٔ (سوره، آیه، شماره واژه) انجام می‌شود؛ تطبیق رشته‌ای
  تنها به‌عنوان کنترل کیفیت به‌کار می‌رود.

## مدل داده (SQLite)

- `surahs(index_, ayas, name_ar, name_en, tname, type)`
- `ayat(surah, ayah, text)` — متن مرجع، بدون بسم‌الله تکراری.
- `words(surah, ayah, word_pos, buck, arabic, surface, norm)`:
  - `surface` فرم واقعی متن مرجع (نمایش در گزارش)
  - `arabic` فرم بازگشایی‌شده از داده صرفی (تحلیل)
  - `norm` فرم نرمال برای جست‌وجو
- `segments(surah, ayah, word_pos, seg_pos, buck, tag, lemma, lemma_norm, root, features)`

ایندکس‌ها روی `words.norm` و `segments.root` قرار دارند.

## هم‌ترازی متن و صرف

1. متن Tanzil به توکن‌ها شکسته می‌شود و بسم‌الله ابتدای سوره‌ها (به‌جز ۱ و ۹)
   با مقایسهٔ نرمال حذف می‌شود.
2. اگر تعداد واژه‌های دو منبع برابر باشد، تراز مستقیم موقعیتی است.
3. در آیه‌های اندک دارای اختلاف نسخه، تراز با LCS روی فرم نرم انجام می‌شود.
4. واژه‌های بدون تراز با `surface = NULL` ذخیره می‌شوند و از فرم تحلیل صرفی
   برای جست‌وجو استفاده می‌کنند.

## نگاشت Buckwalter

داده Corpus با Buckwalter کدگذاری شده است. نگاشت نویسه‌به‌نویسه در
`src/buckwalter.py` است و با اسکریپت `scripts/derive_buckwalter.py` از خود داده
واقعی استخراج و اثبات شده است (بدون حدس دستی برای نویسه‌های نادر).

## رفع ابهام

معیار: اگر فرم نرمال ورودی به بیش از یک ریشه در Corpus مربوط باشد، ابهام
اعلام می‌شود. فهرست گزینه‌ها شامل ریشه، تعداد رخداد و چند واژه نمونه است.
کاربر با ارسال شماره انتخاب می‌کند. وضعیت انتخاب در حافظه و به‌ازای هر
`chat_id` نگه‌داری می‌شود و با ورودی جدید پاک می‌شود.

## هم‌زمانی و تکرار

- پردازش پیام‌ها متوالی است؛ قفل داخلی از پردازش هم‌زمان یک گفت‌وگو جلوگیری می‌کند.
- آفست `getUpdates` تضمین می‌کند هر update یک‌بار پردازش شود.
- پس از ارسال، وضعیت ابهام پاک می‌شود تا نتیجه دوباره ارسال نشود.

## محدودیت‌های طراحی

- بدون پایگاه داده آنلاین؛ SQLite برای اجرای محلی کافی است.
- بدون وابستگی به SDK سنگین؛ درخواست‌های HTTP ساده و قابل آزمون.
- داده‌های مرجع در مخزن نیستند تا مجوزها و حجم مخزن رعایت شود.
